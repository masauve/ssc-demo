# LVMS: split NVMe and HDD into separate volume groups (sno1)

**This destroys every PVC on `lvms-vg1`.** Nothing here is applied by Argo CD.
Run it by hand, in order, in a maintenance window.

## Why

The original `LVMCluster` had no `deviceSelector`, so LVMS built `vg1` from
every empty disk it found:

| Device | Model | Notes |
|---|---|---|
| `nvme0n1` | WD_BLACK SN770 2TB | ~0.1 ms writes, sat idle |
| `sda` | Seagate ST8000DM004 8TB (5400 rpm, SMR) | ~80% of the VG, 100% busy, ~48 ms flushes |
| `nvme1n1` | ADATA SX8200 | OS disk, not in any VG (etcd is here and is fine) |

The thin pool's extents mostly landed on the HDD, so every PVC ran at HDD
speed. Postgres writes on `lvms-vg1` averaged 30 to 130 ms, and a crash-recovery
fsync of an almost empty data directory took more than 50 s.

LVMS cannot remove a disk from an initialized VG (its webhook refuses with
`device paths can not be added after a device class has been initialized`). You
can't `pvmove` the data off the HDD either, because the ~9 TB thin pool does not
fit on the 2 TB NVMe and thin pools cannot shrink. Rebuilding is the only fix.

After the rebuild:

* `lvms-vg1` is the NVMe only and stays the **default** StorageClass, under the
  same name, so nothing that references it needs changing.
* `lvms-hdd` is the HDD only. Workloads opt in per PVC.

## 0. Before you start

Every PVC currently on `lvms-vg1` (as of 2026-11-13):

```
oc get pvc -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,SC:.spec.storageClassName,SIZE:.spec.resources.requests.storage | grep lvms-vg1
```

Decide what each one is worth.

| Keep: back up first | Regenerated by Argo CD or by its operator |
|---|---|
| `artifactory/*` (Maven mirror cache: rebuildable, but slow) | `keycloak/keycloak-db`, `trusted-profile-analyzer/tpa-postgresql` |
| `stackrox/*` (ACS Central DB, policies, violations history) | `gitlab/*` (re-seeded by the GitLab init Job) |
| `nexus/nexus-data` | `quay-registry/*` (re-seeded, but **pushed images are lost**) |
| `openshift-image-registry/image-registry-storage` (internal images) | `trusted-artifact-signer/*` (**new Fulcio/Rekor roots**: old signatures stop verifying) |
| `floorplan/*`, `keycloak26/*`, `tpa-system/*`, `lightwell-demo-ci/*` (not this demo; ask the owners) | `openshift-pipelines/postgredb-tekton-results-*` |
| `openshift-storage/noobaa-*` (object buckets: Quay blobs, RHTPA S3) | |

Back up the "keep" column the way each product supports: `pg_dump` for the
Postgres-backed ones, ACS's own backup, `oc rsync` for plain file volumes. A
volume snapshot will not survive, because snapshots live in the same thin
pool you are about to delete.

Also confirm that the LVMS operator itself is healthy:

```
oc -n openshift-lvm-storage get csv,subscription,lvmcluster
```

## 1. Stop Argo CD from recreating PVCs

Each `ssc-*` Application has `selfHeal: true`. If you delete a PVC, Argo
recreates it in the old VG within seconds and blocks the teardown. Turn off
automated sync on every Application that owns a PVC:

```
for a in $(oc -n openshift-gitops get applications.argoproj.io -o name); do
  oc -n openshift-gitops patch $a --type json -p '[{"op":"remove","path":"/spec/syncPolicy/automated"}]' 2>/dev/null
done
```

Do the same for anything else that reconciles PVCs: the Artifactory
Application, and operator CRs such as the ACS `Central`, the `QuayRegistry`
and the NooBaa `NooBaa` CR. Either scale those operators to 0 replicas or
delete the CRs.

## 2. Delete the workloads, then the PVCs

Scale the StatefulSets and Deployments that mount the volumes to 0, or delete
their namespaces outright if the namespace is fully regenerated. Then:

```
oc get pvc -A --no-headers -o custom-columns=NS:.metadata.namespace,N:.metadata.name,SC:.spec.storageClassName \
  | awk '$3=="lvms-vg1"{print $1, $2}' \
  | while read ns n; do oc -n $ns delete pvc $n --wait=false; done

oc get volumesnapshot -A          # delete any that use lvms-vg1
```

Wait until LVMS has released every logical volume:

```
oc get pv | grep lvms-vg1         # must be empty
oc get logicalvolumes.topolvm.io  # must be empty
```

If a PVC hangs in `Terminating`, a pod still mounts it:
`oc get pods -A -o json | jq -r '.items[] | select(.spec.volumes[]?.persistentVolumeClaim.claimName=="<pvc>") | .metadata.namespace+"/"+.metadata.name'`

## 3. Delete the LVMCluster

```
oc -n openshift-lvm-storage delete lvmcluster lvmcluster
oc -n openshift-lvm-storage get lvmcluster        # wait until gone
```

The operator removes the thin pool, `vg1`, the `lvms-vg1` StorageClass and
the VolumeSnapshotClass as part of its finalizer. It refuses while any
logical volume still exists, which is why step 2 has to finish first.

## 4. Verify the node, and wipe both disks

```
oc debug node/sno1 -- chroot /host sh -c 'vgs; pvs; lsblk -f /dev/nvme0n1 /dev/sda'
```

`vg1` must be gone. LVMS refuses to adopt disks that still carry LVM or
filesystem signatures, so wipe them. Use the by-id paths, never `sdX`, and
check twice that neither one is the OS disk (`nvme-ADATA_SX8200PNP_...`):

```
oc debug node/sno1 -- chroot /host sh -c '
  wipefs -a /dev/disk/by-id/nvme-WD_BLACK_SN770_2TB_24224S804118
  wipefs -a /dev/disk/by-id/ata-ST8000DM004-2U9188_ZR15NYXA
  lsblk -f /dev/nvme0n1 /dev/sda'
```

As an alternative, uncomment `forceWipeDevicesAndDestroyAllData: true` in
`lvmcluster.yaml` and LVMS will wipe the disks itself. Remove it again
afterwards, so a future re-apply can never wipe a disk that is in use.

## 5. Apply the new LVMCluster

```
oc apply -f automation/cluster/lvms/lvmcluster.yaml
oc -n openshift-lvm-storage get lvmcluster lvmcluster -o jsonpath='{.status.state}{"\n"}'   # Ready
oc -n openshift-lvm-storage get lvmcluster lvmcluster -o json | jq '.status.deviceClassStatuses[] | {name, devices: .nodeStatus[].devices}'
oc get sc
```

Expected result: `vg1` contains only `/dev/nvme0n1`, `hdd` contains only
`/dev/sda`, and the StorageClasses are `lvms-vg1 (default)` and `lvms-hdd`.

Confirm that each thin pool sits on the right disk:

```
oc debug node/sno1 -- chroot /host sh -c 'lvs -a -o lv_name,vg_name,lv_size,devices vg1 hdd'
```

After a day of normal use, the Prometheus query
`rate(node_disk_io_time_seconds_total{device="sda"}[5m])` should be near 0
unless something is deliberately on `lvms-hdd`.

## 6. Move bulk data to `lvms-hdd` (optional)

Good candidates, because they are large, sequential, and not fsync-bound:

* `openshift-image-registry` storage (500Gi). Recreate the PVC with
  `storageClassName: lvms-hdd` before the registry operator recreates it, or
  set it under `spec.storage.pvc.claim` in `configs.imageregistry/cluster`.
* `stackrox/central-db-backup` (200Gi).
* The NooBaa default backing store, but **not** `noobaa-db-pg-*`.

Keep every database (`*-postgres*`, `*-db*`, `trillian-mysql`), GitLab, and
Keycloak on `lvms-vg1`.

## 7. Bring everything back

1. Restore the backups from step 0.
2. Re-enable automated sync. Re-running the bootstrap command (RUNBOOK §5)
   puts `syncPolicy.automated` back on every `ssc-*` Application:
   ```
   helm template ssc automation/gitops/bootstrap-infra -f /tmp/ssc-demo-values.yaml | oc apply -f -
   ```
   Re-enable Artifactory's Application the same way, from its own manifest.
3. Scale the operators from step 1 back up, or recreate their CRs.
4. RHTAS gets new signing roots, so re-sign or re-push any images whose
   signatures the demo depends on.
